# 설계

## 문제

여러 장의 VRChat 이미지를 열어 프린트면 프레임을 걷어 내고, 이미지마다 회전·반전과 보정을 적용해 무손실 PNG로 저장하는 정적 웹 앱이다. 모양이 뻔하지 않은 이유는 네 가지다.

- 캔버스 `toBlob` 은 부가 청크를 버린다. 그래서 저장은 "렌더 → PNG 인코딩 → 원본 XMP iTXt 청크를 바이트째 다시 끼우기" 순서가 된다.
- 2048x1440 프린트 40장을 모두 디코딩해 두면 약 470 MB다. 전체 해상도 픽셀을 이미지별 상태로 들고 있을 수 없다.
- 미리보기와 저장 결과가 어긋나면 안 된다. 그러면서도 미리보기는 휴대폰에서도 빨라야 한다.
- 다섯 언어(`ko`, `en`, `ja`, `zh-Hans`, `zh-Hant`)의 번역이 라이브러리 없이 빠짐없이 유지돼야 한다.

실측으로 확인한 제약은 다음과 같다. 프린트는 2048x1440이고 사진은 (64, 69)에서 시작하는 1920x1080 영역이다. 위·왼쪽·오른쪽 여백은 순백이다. XMP는 IHDR 바로 뒤의 iTXt 청크에 있고 방향 정보는 없다. 캔버스 `filter` 는 쓰지 않는다.

## 사용 (호출자 관점)

사용자가 읽는 설명:

> VRChat 프린트나 사진을 끌어다 놓거나 "이미지 열기"를 누르세요. 프린트는 흰 프레임과 캡션이 자동으로 잘리고, 다른 이미지는 그대로 둡니다. 여러 장을 열었다면 아래 썸네일 줄에서 이미지를 고르고, 회전·반전하거나 보정 슬라이더를 움직이고, 필요하면 "레이어 추가"로 사진에 맞는 색 레이어를 얹은 뒤 저장하세요. "자동 보정"을 누르면 보정 슬라이더 값이, "자동 레이어"를 누르면 사진에 필요한 색 레이어가 채워집니다. 프린트는 `<이름>_crop.png`, 그 밖의 이미지는 `<이름>_edit.png` 로 저장됩니다. VRChat 메타데이터(월드, 촬영자, 날짜)는 파일에 남습니다. 아무것도 업로드되지 않습니다.

코드 안의 호출 지점:

```ts
// App.svelte: 열기, 편집, 저장
const { source, thumb } = await openSource(file);                  // 한 번 디코딩, 판별, XMP 보관, 썸네일
draw(thumbCanvas, render(item.thumb, item.edit));                  // 썸네일·미리보기·저장이 같은 render
updateEdit((e) => setAdjust(e, "contrast", Number(input.value))); // 선택된 이미지에 적용
updateEdit(rotateRight);
const { name, blob } = await exportSource(item.source, item.edit); // 전체 해상도 + XMP + 파일 이름
```

```ts
// edit.test.ts: node, DOM 없음
const edit = flipHorizontal(rotateRight(IDENTITY_EDIT));
expect(render(src, edit)).toEqual(naiveFlipH(naiveRotateCW(src)));
expect(render(src, IDENTITY_EDIT).data).toEqual(src.data);
```

## 구조

| 파일 | 맡는 것 | DOM |
|---|---|---|
| `src/edit.ts` | `Pixels`, `Rect`, `Edit`(D4 방향 + 보정 여섯 값 + 색 레이어 목록), 편집 전이 함수, `render` | 없음 |
| `src/print.ts` | 프린트 규격, `classify`, `outputName` | 없음 |
| `src/png.ts` | `XmpChunk` 브랜드, `findXmpChunk`, `withXmp` | 없음 |
| `src/source.ts` | `openSource`, `readSource`, `exportSource` | 있음 |
| `src/i18n.svelte.ts` + `src/locales/*.ts` | 현재 언어(`i18n.locale`, `$state`), `pickLocale`, `t` | 없음 |
| `src/App.svelte` | 열린 이미지와 썸네일 줄, 선택, 미리보기 캐시, 열기·저장 | 있음 |
| `src/AdjustPanel.svelte`, `src/LayerCard.svelte`, `src/Icon.svelte` | 보정 패널, 레이어 카드 하나, 선 아이콘 | 있음 |
| `src/main.ts` | `App` 을 `document.body` 에 띄운다 | 있음 |

**데이터.**

- `Edit = { orientation: { turns: 0|1|2|3, flip }, adjust: Record<AdjustKey, number> }` 는 불변 값이다. 방향은 D4 군의 원소라서 어떤 버튼 순서도 8가지 중 하나로 접힌다. 화면 기준 좌우 반전은 `turns = (4 - turns) % 4` 규칙 하나로 `flipHorizontal` 에만 있다(model-the-domain).
- `Source = { file, kind, rect, xmp }` 는 `openSource` 가 한 번 만들고 바뀌지 않는다. `kind` 와 `rect` 는 같은 `classify` 호출에서 나오므로, 프린트인데 자르는 영역이 다른 상태는 생길 수 없다. 픽셀은 들고 있지 않다.
- `Item = { id, source, thumb, edit }` 는 `App.svelte` 에만 있다. `items` 는 `$state.raw` 배열이고, `edit` 을 바꾸는 곳은 `updateEdit` 하나다. 바뀐 항목만 새 객체가 되므로 다른 썸네일은 다시 그리지 않는다.

**흐름.**

```
File ─openSource─► Source{kind,rect,xmp} + thumb(240px)       [한 번 디코딩 후 픽셀 버림]
선택 ─readSource(source, 1280)─► 미리보기 Pixels (선택된 한 장만 캐시)
슬라이더·회전 ─updateEdit─► item.edit ─rAF─► render(미리보기, edit) ─► 캔버스
                                     └─────► render(thumb, edit)   ─► 썸네일
저장 ─exportSource─► readSource(전체) ► render ► toBlob PNG ► withXmp ► {name, blob}
```

**핵심 결정.**

1. **썸네일, 미리보기, 저장이 `render(src, edit)` 하나를 쓴다.** 셋은 입력 해상도만 다르다. 두 번째 경로가 없으니 어긋날 수 없다. 보정은 256칸 표 세 개(색온도 → 검정 계열 → 노출 → 밝기 → 대비)와 픽셀별 채도 혼합으로 미리 계산한다. 색 레이어는 채도 혼합 뒤에 아래 레이어부터 차례로 겹친다. 채널마다 따로 계산되는 혼합 모드는 레이어마다 표 세 개로 미리 계산한다. `render(src, IDENTITY_EDIT)` 는 바이트가 같다.
2. **자르기는 디코딩할 때 `drawImage` 의 원본 영역으로 한다.** 배율 1이면 정확한 복사다. 축소도 같은 호출에서 하므로 `readSource` 가 사진 픽셀을 얻는 유일한 길이고, 앱이 보는 모든 픽셀은 이미 잘려 있다.
3. **`source.ts` 가 깊은 모듈이다.** 세 함수 뒤에 `colorSpaceConversion: "none"`·`premultiplyAlpha: "none"` 디코딩, 캔버스 읽기, 자르기, 축소, PNG 인코딩, XMP 끼우기, 이름 짓기를 숨긴다. ESLint `no-restricted-imports` 로 `print.ts` 와 `png.ts` 는 `source.ts` 만 가져오게 막는다(importable-internals). ESLint는 접근 제어자 규칙 때문에 어차피 들어간다.
4. **XMP는 청크 통째로 옮긴다.** `findXmpChunk` 는 길이·타입·데이터·CRC를 그대로 잘라 `XmpChunk` 로 표시한다. `withXmp` 는 그 청크를 오프셋 33(IHDR 바로 뒤)에 넣고, 이미 있는 XMP는 먼저 지워 두 번 넣어도 결과가 같다. `findXmpChunk` 는 사용자 파일을 받는 신뢰 경계라서 잘못된 입력에 예외 대신 null을 돌려준다. `withXmp` 의 입력은 우리가 만든 캔버스 출력이므로 모양이 틀리면 버그로 보고 예외를 던진다(boundary-discipline).
5. **목록은 한 곳에만 둔다.** 슬라이더는 `ADJUST_KEYS`, 혼합 모드 선택과 그 계산식은 `BLEND_MODES`, 회전 버튼은 `ORIENT_ACTIONS`, 언어는 `DICTIONARIES` 에서 만든다. 다른 언어 사전은 `Dict` 타입이라 키가 빠지거나 남으면 타입 오류다. 프린트 여백 띠 `MARGIN_STRIPS` 는 `PRINT_PHOTO` 에서 계산하므로 판별과 자르기가 같은 상수를 본다.
6. **화면은 Svelte 5 컴포넌트다.** 화면 글자는 템플릿에서 `t(key)` 로 넣는다. `t` 는 `$state` 인 `i18n.locale` 을 읽으므로, 언어를 바꾸면 그 글자만 다시 그려진다. 글자가 없는 아이콘 버튼과 미리보기 캔버스는 `aria-label` 과 `title` 에 `t(key)` 를 쓴다. `index.html` 에는 화면 요소가 없다. 편집 규칙은 계속 DOM 없는 `edit.ts` 에 있고, 컴포넌트는 그 전이 함수를 부를 뿐이다.
7. **잠금 없이 비동기를 다룬다.** 파일은 순서대로 열어 한 번에 디코딩 한 장만 메모리에 둔다. 선택이 바뀐 뒤 늦게 끝난 디코딩은 버린다. 저장은 시작할 때 `edit` 을 복사해 두고 쓴다.

검증은 세 경계에 있다. `setAdjust` 는 슬라이더 값을 [-100, 100]으로 자르고 반올림한다(NaN은 0). `setLayerColor` 는 `#rrggbb` 만, `setLayerMode` 는 `BLEND_MODES` 의 키만 받고, `setLayerOpacity` 는 [0, 100]으로 자른다. `pickLocale` 은 저장된 값이 유효한 언어일 때만 받는다. `findXmpChunk` 는 파일 바이트를 검사한다. 경계 안쪽은 타입을 믿는다.

**하지 않는 것.** 실행 취소, 목록에서 지우기, 새로고침 뒤 편집 유지, Worker, 선형 색공간 연산, ICC 처리, ZIP, 전체 적용, 자유 각도 회전, 수동 자르기.

**인터페이스 깊이.** UI가 아는 것은 `openSource`, `readSource`, `exportSource`, `render`, 열세 개의 `Edit` 전이 함수, `i18n`/`t`/`pickLocale`/`storeLocale` 이다. 그 뒤에 프린트 규격, 청크 탐색, 디코딩 옵션, 축소, 색 연산, 방향 대수가 숨는다.

## 합성 결정

모델 네 개(opus, fable, sonnet, haiku)가 따로 후보를 냈다. 교차 심사(fable)와 직접 채점 모두 opus 후보를 베이스로 골랐다. 심사 점수는 opus 28, sonnet 26, fable 23, haiku 19였다.

- **베이스 opus:** 여백 띠의 행 범위를 캡션 위로 한정했고, `premultiplyAlpha: "none"` 을 지정했으며, 멱등 splice와 잘린 파일 처리를 갖췄다. 브라우저 경계를 `source.ts` 하나에 모았다.
- **sonnet에서 가져옴:** 여백 띠를 `PRINT_PHOTO` 에서 계산하는 방식(`MARGIN_STRIPS`). 저장 버튼은 편집기에 하나만 둔다. opus는 목록 행마다 저장 버튼을 두어 같은 일을 하는 길이 둘이었다.
- **fable에서 가져옴:** `detectLocale` 과 `initialLocale` 을 순수 함수 `pickLocale(languages, stored)` 하나로 합쳤다.
- **sonnet 방향으로 바꿈:** `index.html` 의 `data-i18n` 키를 없앴다. opus는 HTML 안의 키를 정규식 테스트로 확인했는데, 그 테스트가 필요 없어진다.
- **버림:**
  - sonnet의 `Session`·이벤트·`Codec` 계층. "목록 하나, 선택 하나"에는 벌지 못한 구조다.
  - haiku의 reducer + session 이중 층.
  - fable의 이미지별 1024px 미리보기 상주. 40장이면 약 100 MB다.
  - 심사가 제안한 "순수 함수 자르기". 전체 해상도 경로와 축소 경로에 자르기가 두 번 생기고, 크롭 정확도는 실제 프린트와 픽셀을 비교하는 검증으로 확인한다.
- **후보에서 발견한 버그:**
  - haiku: 흰색 판정에 `|` 를 써서 254가 섞여도 통과한다.
  - haiku: 좌우 띠를 캡션 행까지 검사한다.
  - haiku: 90° 회전 뒤 반전 합성이 틀렸다.
  - haiku: XMP를 `subarray` 로 잘라 파일 전체 버퍼를 붙잡는다.
  - fable: 없는 사전 파일을 import하고, 청크 길이 검사가 없다.

  모두 베이스에는 해당하지 않는다.

## 받아들인 트레이드오프

- 선택과 저장 때 파일을 다시 디코딩한다(각 30~80 ms). 대신 메모리는 썸네일 40장과 미리보기 한 장으로 평평하게 유지된다.
- 보정은 감마 인코딩된 sRGB에서 단순 곡선으로 계산한다. 대신 표 세 개로 한 번에 처리하고 테스트가 쉽다. 강한 색온도는 켈빈 모델보다 덜 자연스러울 수 있다.
- 미리보기는 1280px에서 계산한다. 축소 후 보정이라 저장본과 반올림 수준 차이가 있다. 대신 휴대폰에서도 프레임마다 반응한다.
- 40장을 순서대로 연다(몇 초). 대신 메모리가 묶이고 동시성 코드가 없다.
- 상태는 `App.svelte` 의 컴포넌트 상태다. 목록 하나, 선택 하나라 store 계층은 전달만 하는 층이 된다. 보정 패널은 `edit` 과 `onchange(change)` 만 받는다.
- 초기화 버튼은 보정과 색 레이어를 되돌리고 회전·반전은 둔다.
- 색 레이어의 픽셀 모드(어두운 색상, 밝은 색상, 색조, 채도, 색상, 광도)는 표로 줄일 수 없어 픽셀마다 계산한다. 1280x720 미리보기 한 장에 30~45 ms(Chromium)로, 표만 쓰는 편집의 약 25 ms보다 느리고, 이런 레이어를 쌓을수록 더해진다. 대신 썸네일·미리보기·저장이 계속 같은 `render` 하나를 쓴다.

## 고려한 대안

- **이미지마다 전체 해상도 픽셀을 들고 픽셀 단계로 자르기.** 다시 디코딩할 일은 없지만 40장에 약 470 MB이고, 어느 한 경로에서 자르기를 빠뜨릴 수 있다.
- **미리보기만 별도 경로(CSS 회전 + 캔버스 `filter`), 저장 때만 픽셀 연산.** 빨리 만들 수 있지만 같은 일을 두 구현이 해 어긋난다. `filter` 에는 색온도도 없다.
- **단계별 모듈(`load`, `detect`, `crop`, `rotate`, `adjust`, `export`).** 순서도처럼 읽히지만 시간 순 분해다. 픽셀 불변식과 자르기 영역이 다섯 경계를 넘고 호출자가 단계를 조율해야 한다.
- **WebGL 셰이더로 보정.** 미리보기는 빨라지지만 저장용 읽기 경로가 하나 더 생기고 정밀도·컨텍스트 손실을 다뤄야 한다. 2~3 MP에는 필요 없다.

## 테스트 계획

테스트 경계는 두 곳이다. 둘 다 사용자가 관찰할 수 있는 결과만 확인하고, 내부 함수(`classify`, `withXmp` 등)는 직접 부르지 않는다. 테스트 샘플은 테스트 안에서 합성하고, 저장소에 실제 프린트를 넣지 않는다.

**경계 1: 파일 → 저장 PNG (`openSource` + `exportSource`, vitest 브라우저 모드, Playwright Chromium).**
합성 샘플은 흰 여백과 XMP iTXt 청크를 가진 2048x1440 PNG다. 사진 영역은 픽셀값이 모두 다르게 채운다.

- 합성 프린트를 저장하면 1920x1080이고, 원본 (64,69) 영역과 픽셀이 같다. 파일 이름은 `_crop.png` 다.
- 여백 띠 안의 픽셀 하나라도 흰색이 아니면 자르지 않는다. 띠 모서리 네 곳에서 확인한다. 이때 파일 이름은 `_edit.png` 다.
- 캡션 영역이 검어도 프린트로 자른다.
- 1920x1080과 1080x1920 이미지는 그대로 저장한다.
- 저장한 PNG에서 XMP 청크가 원본과 바이트까지 같다. XMP가 없는 입력은 XMP 없이 저장된다.
- 오른쪽으로 한 번 회전한 편집으로 저장하면 1080x1920이다.
- `a.b.PNG` → `a.b_crop.png`, `noext` → `noext_crop.png`, `image.jpg`(사진) → `image_edit.png`.
- 이미지가 아닌 파일은 `openSource` 가 거부한다.

**경계 2: 편집 적용 (`render`, node).** 조합이 많아 브라우저보다 node에서 빠르게 돈다.

- `IDENTITY_EDIT` 는 바이트가 같다.
- 길이 4 이하의 모든 버튼 순서가 단순 회전·반전 함수를 차례로 적용한 결과와 같다(3x2, 픽셀값이 모두 다른 이미지).
- 알파는 바뀌지 않는다.
- 각 슬라이더 0은 그대로다.
- 밝기는 0과 255를 유지한다.
- 채도 -100이면 R=G=B다.
- 색온도 +100이면 회색의 R이 오르고 B가 내린다.
- 슬라이더 값은 [-100, 100]으로 잘린다.
- 초기화는 방향을 유지한다.
- 노출과 검정 계열은 검은색과 흰색 끝을 예상대로 옮긴다. 색온도 ±100에도 순백과 순흑은 그대로다.
- 불투명도 0인 색 레이어는 바이트가 같다. 혼합 모드마다 중립색(어둡게 하는 계열은 흰색, 밝게 하는 계열·차이·제외·빼기는 검은색, 라이트 계열은 회색)은 픽셀을 거의 그대로 둔다. 광도·색상 모드는 회색 레이어에서 회색을 만들고, 하드 혼합은 0과 255만 낸다. 불투명도 50은 절반 지점이다.
- 색 레이어 입력은 잘못된 색, 없는 혼합 모드, 범위 밖 불투명도를 받지 않는다.
- 자동 레이어는 필요한 것이 없는 사진(선명한 여러 색, 색이 있는 그늘, 뭉갠 검정 없음)에 아무것도 깔지 않는다. 한 색조에 몰린 사진에는 그 색조의 소프트 라이트, 물 빠진 사진에는 색상 번, 회색 그늘에는 보색의 어두운 소프트 라이트, 뭉갠 검정에는 스크린을 깔고, 뭉갠 부분이 넓을수록 불투명도가 높다.
- 자동 레이어는 있던 레이어를 모두 바꾸고, 두 번 눌러도 결과가 같으며, 보정까지 적용한 사진으로 잰다.
- 레이어 추가는 자동 레이어가 깔 레이어 가운데 아직 없는 것을 하나씩 더하고, 다 있으면 사진 색조의 소프트 라이트를 차례로, 색조가 없으면 `NEW_LAYER` 를 더한다.
- 색 레이어는 아래부터 차례로 겹치고, 각 레이어는 아래 레이어까지 겹친 결과를 받는다. 추가는 맨 위에 놓고, 삭제와 값 변경은 고른 레이어만 바꾸며, 이동은 이웃과 자리를 바꾸고 끝에서는 그대로다.
- 자동 보정은 가득 찬 회색 기울기를 거의 그대로 두고, 밝은 이미지를 어둡게 하지 않는다.
- 자동 보정은 어두운 이미지를 중간 회색 쪽으로 일부만 올리고, 뿌연 이미지의 검정과 흰색 끝을 넓힌다.
- 자동 보정은 무채색 픽셀의 색 틀어짐을 30~70%만 지우고, 무채색 픽셀이 없는 사진의 색온도는 건드리지 않는다.
- 자동 보정은 방향, 채도, 색 레이어를 유지하고, 두 번 눌러도 결과가 같다.

**테스트로 잡지 않는 것.** 언어 선택(`pickLocale`)과 화면 연결은 배포본을 열어 직접 확인한다.

**배포 전 수동 검증.** 실제 프린트 몇 장을 저장해 두 가지를 비교한다.

- 원본 (64,69) 1920x1080 영역과 픽셀이 같은지
- XMP가 원본과 바이트까지 같은지

## 구현 반영

- `updateEdit(id, change)` 를 `updateEdit(change)` 로 줄였다. 편집을 바꾸는 호출자는 모두 선택된 이미지를 고친다. 썸네일과 미리보기를 다시 그리는 길은 여전히 이것 하나다.
- 첫 화면의 언어 추측은 저장하지 않는다. 사용자가 언어를 고를 때만 `storeLocale` 로 저장한다. 첫 방문에 추측한 언어가 저장되면 브라우저 언어를 바꿔도 따라가지 않기 때문이다.
- 여백 띠는 사진 경계에서 1px 떨어진 곳부터 검사한다(`BLEED`). 실제 프린트 37장 중 3장에서 사진 바로 위 줄(y=68)이 사진 색으로 번져 있었고, 그 때문에 프린트로 판별되지 않았다. 번짐은 그 한 줄에만 있었고 사진 영역 (64, 69, 1920, 1080)은 그대로다.
- `classify(width, height, readPixels)` 는 크기가 프린트와 같을 때만 픽셀을 읽는다. 큰 일반 사진을 판별하려고 통째로 복사하지 않는다.
- 여러 번 끌어다 놓아도 열기는 앞의 열기가 끝난 뒤에 시작한다(`opening` 사슬). 디코딩은 언제나 한 장이다.
- 상태줄은 메시지마다 새 줄을 더한다. 같은 메시지가 반복돼도 스크린리더가 다시 읽고, 여러 파일의 실패가 모두 남는다. 상태줄은 비어 있어도 접근성 트리에 남도록 숨기지 않는다.
- 선택을 바꾸면 새 미리보기가 준비될 때까지 이전 미리보기를 숨긴다.
- 사전에 `preview`(미리보기 캔버스 이름)와 `adjustments`(보정 패널 제목) 키를 더했다. 저장 버튼 문구는 [디자인 규칙](design.md)의 시안대로 "PNG로 저장"이다.
- 캔버스는 `OffscreenCanvas` 를 쓴다. 디코딩·읽기·인코딩이 DOM 요소를 만들지 않는다.
- 내려받기 링크의 객체 URL은 10초 뒤에 해제한다. `click()` 직후에 해제하면 일부 브라우저에서 내려받기가 취소된다.
- 파일 열기는 `<button>` 이 숨긴 `<input type="file">` 을 누른다. `<label>` 은 키보드로 초점을 받지 못한다.
- 자동 보정(`autoAdjust(edit, thumb)`)은 썸네일을 재서 색온도 → 검정 계열 → 노출 → 밝기 순서로 값을 정하고, 각 단계는 앞 단계까지 적용한 `render` 결과를 잰다. 그래서 값이 사용자가 보는 곡선과 맞는다. 처음 만든 판(평균 R·B를 맞추는 색온도, 중앙 밝기를 중간 회색으로 옮기는 밝기, 대비 늘이기)은 실제 프린트 5장 중 1장만 나아졌다. 밝은 사진을 어둡게 했고, 하얀 부분을 노랗게 물들였고, 피부와 월드 조명 색을 지웠다. 그래서 세 가지를 바꿨다.
  - 색온도는 무채색 픽셀(채널 최대·최소 차가 최대의 15% 미만, 잘리지 않은 것)이 5% 이상일 때만 재고, 그 픽셀의 평균 R·B를 맞추는 값의 절반을 ±30 안에서 쓴다. 기준을 30%로 두면 피부색이 무채색으로 잡혀 얼굴이 차가워졌다.
  - 검정과 흰색 끝은 픽셀별 채널 최소의 0.5%, 최대의 99.5% 지점으로 정한다. 밝기 대신 채널 끝을 보므로 색 조명이 잘리지 않는다. 노출은 올리기만 하고 +50에서 멈춘다. +57에서 머리카락이 날아갔다.
  - 밝기는 로그 평균 밝기가 0.42보다 어두울 때만 그 거리의 60%를 올리고 +60에서 멈춘다. 어둡게 하지 않는다. 대비는 0으로 둔다.
- 노출과 검정 계열을 보정에 더했다. 밝기(감마)와 대비(가운데 회색 축)만으로는 한쪽 끝만 늘일 수 없어서, 검정이 이미 0인 밤 사진을 밝히면 그늘이 떴다.
- 색온도는 채널 이득 대신 채널별 거듭제곱 곡선이다. 중간 회색의 변화량은 예전 이득(±20%)과 같고, 0과 255는 움직이지 않는다. 이득 방식은 흰 부분에서 R이 255에 막히고 B만 줄어 하얀 곳이 노래졌다.
- 색 레이어는 사람들이 VRChat 사진 위에 단색 레이어를 혼합 모드로 깔아 분위기를 내는 작업을 옮긴 것이다. 혼합 모드는 포토샵 목록 26가지를 모두 둔다. `BLEND_MODES` 는 채널마다 따로 계산되는 모드(`kind: "channel"`, 표 세 개로 미리 계산)와 세 채널을 함께 보는 모드(`kind: "pixel"`, 어두운 색상·밝은 색상·색조·채도·색상·광도, 픽셀마다 계산)를 나누는 표다. 디더 합성(Dissolve)만 뺐다. 픽셀마다 무작위 점을 찍는 모드라 썸네일, 미리보기, 저장본의 해상도마다 결과가 달라져 "셋이 같은 `render`" 원칙을 깬다.
- 색 레이어는 여러 장을 쌓는다. `Edit.layers` 는 아래부터 위 순서의 배열이고, 화면의 카드 목록은 포토샵처럼 맨 위 레이어를 먼저 보인다. 카드는 레이어 위치를 키로 그리므로, 값이 바뀌어도 그 자리의 입력 요소는 그대로다. 그래서 슬라이더를 끄는 동안 입력 요소가 바뀌지 않는다.
- 자동 레이어(`autoLayers(edit, thumb)`)는 정해 둔 레이어 세트가 아니라, 사진에서 잰 문제마다 레이어를 한 장씩 둔다. 처음 판은 사진 밝기에 따라 모드를 고르는 기준을 실제 프린트 81장의 분포에서 정했는데, 그러면 특정 사용자의 사진에 맞춘 프리셋이 된다(사용자 결정으로 폐기). 지금 기준은 각 사진 안에서 재는 값이다.
  - 색조는 채도×밝기로 가중한 36칸 색조 히스토그램에서 30° 이상 떨어진 봉우리를 많은 순서로 최대 넷 고르고, 회색·어두운·물 빠진 픽셀은 세지 않는다. 가장 많은 색조가 색 전체의 절반 이상이면 그 색조의 소프트 라이트를 10~20%로 깐다. 이미 있는 색 틀어짐을 더 키우므로 약하게 둔다. 30%까지 올렸을 때는 피부가 주 색조인 프린트가 분홍으로 물들었다.
  - 밝은 픽셀의 평균 채도가 0.3 미만이면 주 색조의 옅은 색상 번을 10~40%로 깐다.
  - 가장 어두운 30% 픽셀의 평균색 채도가 0.1 미만(회색 그늘)이면 보색의 어두운 소프트 라이트(HSV 0.7, 0.35)를 15~35%로 깐다. 보색에서 60° 안에 사진 자신의 색조가 있으면 그 색조를 쓴다. 처음에는 같은 색을 스크린 30%로 깔았는데, 검정이 그 색으로 떠서 뿌옇게 보였다. 소프트 라이트는 검정을 띄우지 않는다.
  - 밝기 10/255 미만 픽셀이 2%를 넘으면 주 색조의 어둡고 회색에 가까운 스크린을 10~30%로 깐다. 보색을 쓰면 분홍 사진의 검정이 녹색으로 떴다.
  - 불투명도는 문제가 클수록 높고, 보이는 최소값인 10%에서 시작한다. 처음 판은 뭉갠 정도에 그대로 비례해 2~5%짜리 보이지 않는 레이어를 깔았다.
- 레이어 추가(`addLayer(edit, thumb)`)는 자동 레이어가 깔 레이어 가운데 아직 없는 것을 먼저 더한다. 그래서 하나씩 눌러도 자동 레이어와 같은 결과에 닿는다.
- 화면을 Svelte 5로 옮겼다(사용자 결정). DOM을 직접 만들던 `main.ts` 의 `label`/`accessibleName`/`STATIC_LABELS` 와 레이어 카드 재생성 코드가 템플릿으로 바뀌었다. 타입 검사는 `svelte-check` 가 `.svelte` 와 `.ts` 를 함께 본다. ESLint는 `eslint-plugin-svelte` 로 `.svelte` 도 검사하고, 가져오기 제한 규칙도 `.svelte` 에 건다. 미리보기 캔버스의 `role="img"` 는 Svelte 접근성 경고를 끄고 유지했다. 사진을 나타내는 그림이기 때문이다.
- TypeScript는 6.0으로 고정했다. typescript-eslint 8.72가 6.1 미만만 지원한다.
- CI에 `pnpm run lint` 단계를 더했다. 접근 제어자와 가져오기 제한 규칙이 린트에만 있기 때문이다. 손으로 다시 배포할 수 있게 `workflow_dispatch` 도 켰다.

## 열린 질문과 위험

- VRChat PNG가 16비트이거나 ICC·gAMA 청크를 갖는 경우가 있을까? 캔버스는 8비트로 줄인다. 확인한 37장은 IHDR, iTXt, IDAT, IEND뿐이었다.
- 데스크톱 큰 화면에서 미리보기 1280px이 충분할까, 아니면 `devicePixelRatio` 에 맞춰야 할까?
- 대비(2^(1.5k))와 색온도(중간 회색 ±20%) 상수는 실제 프린트로 한 번 맞춰 본 뒤 테스트로 고정해야 한다.
- 8K 같은 큰 일반 사진은 "수 메가픽셀" 가정을 넘는다. iOS 캔버스 한도에 걸릴 수 있다.
